# Замер фиксированного тика ARPG и опыт с копированием при записи

[English](../../../evidence/rv-c-arpg/README.md) | [Русский](README.md) | [Документация](../../README.md)

Пять копий для отката занимали **36,92 мкс (3,85%)** исходного тика.
Вариант с копированием при записи сократил эту часть до **13,00 мкс (1,38%)**.
Медиана средних по семи прогонам изменилась с **966,0 до 962,6 мкс**.
Разница внутри пар составила от −5,80% до +3,32% (медиана −2,06%). В исходном
варианте преобразования `ArpgFrame` в JSON и обратно вместе с копией перед
десериализацией занимали **463,03 мкс (48,31%)**. [Замеры и хеши отчётов](../../../evidence/rv-c-arpg/measurements.json)

## Нагрузка и метод

База `9aa0e7633b2bfbf87fbd7d89bb6c6085cc04c8c5`, Windows x64 `26300.10075`,
Ryzen 9 3900X, Rust `1.99.0` x86_64-pc-windows-msvc, Release `opt-level=2`.
Один поток выполнял фиксированный тик `1/60` с через `GameHost` без рендера,
с ECS, восемью нативными узлами ARPG и сценой **Small monsters** из Two Arenas.
Фикстура подняла здоровье обеих сторон до 10 000, сохранила исходные точки
появления и повторяла детерминированные команды движения и ближнего боя.
Все 20 врагов оставались живы. В каждом зачётном прогоне по 600 тиков
зарегистрированы 159 событий `Attack`, 391 `Hit` и 550 `Sound`. Рендер,
компилируемые Custom и внешние сервисы были вне фикстуры.
[Сцена Two Arenas](../../../../crates/example-two-arenas/src/content.rs) · [Фикстура и счётчики](../../../evidence/rv-c-arpg/probe.patch)

Каждый процесс создавал новый `GameHost`, выполнял 120 тиков прогрева и
замерял 600 тиков. Семь пар общего времени прошли последовательно с
чередованием порядка вариантов. Пооперационные таймеры для этих пар были
выключены. Штатный таймер тика измеряет `GameSession` с обработкой входа,
расписанием систем, валидацией и публикацией. Отдельный таймер измеряет весь
вызов `GameHost::step`. Ниже медианы средних и p95 по отдельным прогонам
в микросекундах. Для p95 использован ближайший ранг сверху.

| Объём | Исходное среднее / p95 | Копирование при записи, среднее / p95 |
| --- | ---: | ---: |
| Фиксированный тик | 966,0 / 1332,4 | 962,6 / 1320,0 |
| `GameHost::step` | 968,7 / 1334,9 | 965,3 / 1323,5 |

Разбивку дали пять дополнительных пар с пооперационными таймерами.
Знаменатель — всё время фиксированных тиков в этих парах, по 3000 тиков
на вариант. Малые значения для пустых событий и `control` включают
погрешность таймера. Прототип делит через `Arc` существующие JSON-значения
ресурсов и `module_data`. При записи он заменяет разделяемое значение или
записывает в выделение с единственным владельцем. `control` отделяется при
изменяемом доступе. Копии событий и состояний систем, копирование при
обновлении ресурсов и преобразования `ArpgFrame` выполняют ту же работу
в обоих вариантах. [Прототип](../../../evidence/rv-c-arpg/cow.patch)

На тик пришлось десять чтений и девять записей кадра с учётом `begin_tick`
и финальной валидации. В отдельной паре счётчики за 600 тиков зарегистрировали
95 532 декодирования `actor`, 69 817 `health`, 24 600 `melee` и 12 000 `ai`.
Это 97,96% чтений шести типов компонентов через JSON-функцию ARPG. Счётчик
измеряет частоту обращений. [Решение по типизированному доступу и Bevy](../../decisions.md#rv-c-arpg-tick)

## Поздний отказ через GameHost

Дополнительный узел после звука ARPG изменял JSON-состояние, ресурс,
`module_data`, `control` и событие, затем отклонял тик в `commit_tick`, после
входа в валидацию и публикацию хоста. В обеих сборках принятое состояние
игры, включая мир и идентификаторы времени жизни, ресурсы, состояния систем
и `control`, точно совпало со снимком до отказа. События отклонённого тика
не появились. Повтор через `GameHost::step(0.0, input)` использовал ожидающий
тик и дошёл до тика 121. Новый процесс с тем же входом и без отказа дал те же
хеши состояния и событий. Разные процессы дают одинаковую начальную точку
счётчика идентификаторов времени жизни. Во всех 26 прогонах замера и подсчёта
также совпали хеши фикстуры, финального состояния и полной зачётной серии
событий. [Отчёты об откате и прогонах](../../../evidence/rv-c-arpg/measurements.json)

## Повтор замеров

Соберите оба варианта последовательно во временном архиве исходной базы.
Патчи содержат эксперимент и рассчитаны на указанную цель `example`.
Сохраните исходный EXE перед второй сборкой.

```powershell
$base = '9aa0e7633b2bfbf87fbd7d89bb6c6085cc04c8c5'
New-Item -ItemType Directory work/rv-c4-replay
git archive --format=tar --output=work/rv-c4-main.tar $base
tar -xf work/rv-c4-main.tar -C work/rv-c4-replay
git apply --directory=work/rv-c4-replay docs/evidence/rv-c-arpg/probe.patch
Push-Location work/rv-c4-replay
cargo build --locked --release -p module-engine-host --example rv_c4_arpg
Copy-Item target/release/examples/rv_c4_arpg.exe rv-c4-eager.exe
Pop-Location
git apply --directory=work/rv-c4-replay docs/evidence/rv-c-arpg/cow.patch
Push-Location work/rv-c4-replay
cargo build --locked --release -p module-engine-host --example rv_c4_arpg
Copy-Item target/release/examples/rv_c4_arpg.exe rv-c4-cow.exe
```

Аргументы EXE: `<mode> <new-report.json>`. Выполните семь пар `total`, начав
с исходного варианта, и пять пар `sections`, начав с COW. В каждой следующей
паре меняйте порядок. Выполните по одному `components` для каждого EXE.
Отдельно запустите `rollback` и `oracle` для каждого варианта и сравните
`accepted_before_sha256`, `accepted_after_sha256`, `accepted_events_sha256`
и `ticks_after`. `rollback` также точно сверяет состояние внутри процесса.
Хеши фикстуры, принятого состояния и событий должны совпасть между вариантами
в `total`, `sections` и `components`. Исходные массивы выборок, порядок
запусков, логи сборок и EXE сохранены в локальном `outputs/rv-c/`.

Эксперимент охватывает одну схватку с 20 врагами и один стенд Windows без
рендера. Частота кадров ARPG с рендером, Linux и сравнение разных ECS в эту
проверку не входят. Результат COW относится к трём выбранным категориям
данных и действующему пути преобразований JSON.
