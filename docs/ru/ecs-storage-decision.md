# Решение о хранилище игрового мира

[English](../ecs-storage-decision.md) | [Русский](ecs-storage-decision.md) | [Документация](README.md)

В рабочем движке `GameState.world` хранит игровые данные в `EcsWorld`.
Карта сущностей служит форматом сериализации DTO. См.
[контракт API и времени жизни](ecs-world.md).

<a id="r11"></a>

## R1.1 — гибридное хранение Bevy для миграции

**Переходить к R1.2 с гибридным вариантом.** В свежей парной Release-серии
на нагрузке S3 гибридный тик оказался быстрее `EcsWorld` в **34,82 раза**,
вариант с динамическим JSON — в **4,59 раза**. Оба варианта Bevy прошли
проверки авторских данных на примерах прототипа. Критерий R1.1 требует
ускорения тика S3 минимум в **5 раз** при сохранении этих инвариантов.
Это решение определяет подход для R1.2.

### Варианты хранения

- **Core** использует существующий `EcsWorld` с JSON-столбцами компонентов.
- **Динамический Bevy** заводит отдельный табличный столбец для каждого
  ID компонента через `ComponentDescriptor`, в том числе для компонента со
  значением `null`. В тике JSON-поле движения обновляется через уже
  разрешённый `ComponentId`.
- **Гибрид Bevy** хранит данные движения канонической формы в нативных
  полях `bool` и `f64`, доступных через рефлексию. Поля обновляются
  типизированным запросом Bevy. JSON-кодек проекта восстанавливает те же
  ключи и типы значений. Если исходный payload нельзя восстановить без
  потерь, например при дополнительных полях или другом типе числа, кодек
  сохраняет payload целиком в JSON. Остальные семь компонентов S3 и
  неизвестные ID используют те же JSON-столбцы, что и динамический вариант.

Для нативных компонентов используем гибридный вариант с кодеками без потерь,
а для данных, заданных схемой, сохраняем JSON-столбцы. Это даёт измеренное
ускорение типизированных изменений и точное восстановление payload.
Рефлексия даёт доступ к нативным полям. Кодек проекта определяет формат
сохранения. Протестированный вариант целиком на JSON не проходит порог
тика. Восстановление снимка гибрида дороже Core. Этот результат не
обосновывает восстановление полного снимка на каждом тике. Транзакции
рабочего движка проектируются в R1.4.

Значения в таблице — среднее / p95 по ближайшему рангу в миллисекундах.
Операции жизненного цикла замерены для пакета из 2 000 сущностей.

| Операция | Текущий `EcsWorld` | Bevy с динамическим JSON | Гибрид Bevy |
| --- | ---: | ---: | ---: |
| Тик S3 | 0,5363 / 0,6636 | 0,1168 / 0,1251 | **0,0154 / 0,0153** |
| Создание пакета | 3,8199 / 4,3710 | 4,4148 / 4,9128 | 4,7268 / 5,2546 |
| Удаление пакета | 15,9447 / 17,6617 | 14,8780 / 16,5193 | 14,7157 / 15,6583 |
| Снятие переносимого снимка | 6,9000 / 7,9135 | 5,9892 / 6,7454 | 5,7628 / 6,4403 |
| Восстановление переносимого снимка | 3,1994 / 3,6333 | 4,3411 / 4,9171 | 4,6022 / 5,1340 |

Коэффициент ускорения — отношение средних Core и кандидата по всем
неокруглённым замерам. Свежий замер Core даёт порог **0,1073 мс** для
ускорения в пять раз. Среднее 0,756 мс из R0.6 с нативным окном и
ориентир 0,151 мс — [исторические значения](bench-r06-20261122.md).
Эта серия проходит на CPU без рендера. Нативный протокол
`bench.py --compare` отвечает на отдельный вопрос [«не хуже ли эталона»](bench.md#not-worse).

Редактор и прототип используют общий [генератор данных S3 и тик Core](../../examples/bench/s3_ecs.rs).
В тик входят запрос на наличие всех восьми компонентов у 2 000 сущностей,
выдача полных результатов в порядке стабильных ID, та же формула движения
при шаге времени фикстуры 60 Гц и запись `bench.motion.offset` и локального
Y у первых 1 000 совпадений. Bevy сохраняет дескриптор строки из выборки для
этих записей. Извлечение трансформаций, рендер, планирование систем,
транзакции и работа со снимком измеряются вне этого таймера или оставлены
за пределами серии. Создание и удаление выполняются проверяемыми
пакетами объектов без потомков. Подготовка входов находится вне таймера.
Переносимый снимок — независимая коллекция `GameEntity` со стабильными
ID, трансформациями, родителями, цветом, компонентами и ссылками.
Восстановление проверяет иерархию и ссылки при сборке хранилища.
Кодирование в JSON, I/O и контрольная копия состояния рантайма относятся
к отдельным операциям.

### Проверенные свойства

- У обоих вариантов Bevy полная упорядоченная выборка совпала с Core на
  каждом кадре S3. Все значения сущностей и трансформации совпали на
  кадрах 0, 29, 30 и 269. Перестановка строк и отсутствие компонента
  одинаково меняют выборку и записи во всех трёх реализациях.
- Разрешённый экземпляр префаба сохранил стабильный ID `9007199254740993`,
  родительскую и именованную ссылки на него, точный ключ `Exact-Key`,
  отдельное пространство имён `source.Widget.Other` и вложенный неизвестный
  JSON. Явный `null` остался отличим от отсутствия, целый `0` сохранил
  свой тип, а типизированное число с плавающей точкой сохранило знак
  отрицательного нуля. Сохранение → загрузка → повторное сохранение
  карты DTO со стабильными ID дало те же байты. Байты авторской
  фикстуры сохранились.
- У подготовленного кандидата с битой ссылкой также менялись
  трансформация, payload компонента, счётчик тиков, ресурс и события.
  Отклонение сохранило прежние байты сущностей, дескрипторы Bevy и всё
  проверенное состояние тика. Следующий корректный кандидат
  успешно опубликовался.

Результаты относятся к фикстурам отдельного прототипа. Контракт стабильных ID
и сквозные проверки рабочего движка описаны в [мире ECS](ecs-world.md).
Замер на CPU не показывает ускорение нативного кадра или игрового шага.

`ae2b06b0194d21bc2c64e41af03f631bace3dbe2`, с нативным Rust toolchain и

```sh
cargo fetch --locked --manifest-path crates/ecs-spike/Cargo.toml
python crates/ecs-spike/run.py outputs/bench/r11-reproduction
```

Скрипт выполняет `cargo test` и `cargo build` с `--release --offline

1 440 замеров тика и 180 замеров каждой пакетной операции.

Исходники фикстуры S3 и тика совпадают со снимком замера прототипа.
В нативном сравнении использованы отдельные Release-сборки

## Этап 3 — предыдущее решение о хранении

## Требования

Исходные модули регистрируют динамические ID компонентов и JSON-схемы. Сохранённый ID объекта должен переживать разрешение сцен/шаблонов, команды, экспорт и протокол Rust IPC. Весь мир, значения компонентов, ресурсы и события должны поддерживать независимую контрольную копию для отказа публикации тика. Запросы должны выбирать принадлежность компонентов без просмотра JSON-карты каждого объекта. Извлечение для рендера остаётся нейтральным.

## Сравнение подходов

| Подход | Соответствие требованиям | Дополнительная работа |
| --- | --- | --- |
| Расширить существующие таблицы компонентов `EcsWorld` | Уже есть стабильные ID, детерминированный порядок и независимое клонирование; динамические ID схем могут адресовать колонки напрямую | Колонки компонентов, запросы принадлежности, политика ссылок, проверка контрольных копий и миграция потребителей |
| Внедрить `hecs` | Типизированные запросы компонентов и непрерывное хранение архетипов независимо от нашего планировщика | Сопоставление стабильных ID, кодеки схем/native, детерминированное извлечение и явный снимок/восстановление всех установленных типов компонентов |

[Документация hecs World](https://docs.rs/hecs/latest/hecs/struct.World.html) описывает типизированные запросы и хранение архетипов. [Документация сериализации](https://docs.rs/hecs/latest/hecs/serialize/index.html) требует определённых приложением процедур, поскольку произвольные компоненты могут не реализовывать сериализацию. Это полезные возможности, но они не устраняют требования проекта к динамическим схемам и транзакциям.

Для этой итерации выбираем меньшее расширение `EcsWorld`. Решение основано на контрактах и стоимости миграции, а не на измеренном превосходстве над hecs. Динамические компоненты должны храниться в колонках с индексом по компоненту; transform, parent, color и references принадлежат тому же миру. Перенесённая карта сущностей с названием ECS этому решению не соответствует. Native gameplay читает и обновляет эти колонки; записи в форме сущности являются временными DTO для сериализации/UI/IPC.

Провайдер Object остаётся адаптером совместимости. Его независимая иерархия продолжает обслуживать legacy-примеры, но второй production-реализации игрового мира у него не появляется. Стабильные ID объектов остаются независимыми от дескрипторов хранилища.

## Приёмка и ограничения

Проверить динамические запросы принадлежности/пересечения, полный откат компонентов после ошибки валидации/commit, удаление и повторное использование без унаследованных данных, иерархию и ссылки, детерминированную сериализацию, совместимость шаблонов, извлечение сцены и поведение ARPG. В ECS-маршруте должен быть один владелец изменяемого состояния; совместимая проекция проверяется до публикации. Выбор колонок компонентов не даёт гарантий локальности кеша, параллельных запросов или производительности большого мира.
