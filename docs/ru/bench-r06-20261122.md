# Исходные замеры R0.6 — 22 ноября 2026

[English](../bench-r06-20261122.md) | [Русский](bench-r06-20261122.md) | [Документация](README.md)

Первая серия на `main` после [PR №19](https://github.com/ModuleEngine/ModuleEngine/pull/19)
прошла проверку воспроизводимости. Завершились все 15 зачётных замеров,
максимальный разброс составил **2,39 %** при пределе **5 %**. S1 и S2 во
всех трёх прогонах уложились в применимые бюджеты кадра и памяти. Это
[эталон R0.6](product-roadmap.md#rebuild-r0) для последующих сравнений.

## Воспроизведение и условия

Запускайте на измеренной ревизии исходников, на свободном и разблокированном
рабочем столе. Используйте нативный интерпретатор Python и оставьте окно
бенчмарка открытым и ничем не перекрытым.

```sh
python scripts/bench.py --no-profiling
```

- Windows 11 Pro 26H2, сборка `10.0.26300.10075`, Ryzen 9 3900X (12 ядер,
  24 логических процессора), 63,9 ГиБ памяти видимы ОС, AMD Ryzen Balanced.
  RTX 4080 SUPER, драйвер NVIDIA **617.42**, по данным драйвера 16 376 МиБ
  видеопамяти. Монитор 3440×1440, 144 Гц, масштаб 100 %.
- Нативные окна **1920×1080**. Во всех наблюдениях S1/S2 окно было в фокусе.
  Метаданные кадров были валидны, игра была в Playing, пользовательский
  ввод и ошибки отсутствовали. Опциональное поле видимости Player на этом
  пути недоступно. В S2 было ровно 20 врагов. S3–S5 прошли проверку размера
  клиентской области и состояния свёртывания. Все пять сцен использовали
  WGPU/DX12 для GUI и Vulkan для рендера игры на той же видеокарте без
  чтения пикселей на CPU.
- Запрошен режим без GUI vsync. WGPU сообщил **`Immediate`** для каждой
  сцены в прогреве и зачётных прогонах. Это настроенный режим swapchain.
  Интервалы ниже основаны на наблюдениях приложения. Физический вывод на
  экран и время ожидания показа находятся за рамками протокола.
- Release-сборка `module-engine-editor` с `bench` для `x86_64-pc-windows-msvc`,
  rustc и Cargo 1.99.0, Python 3.12.14, `CARGO_NET_OFFLINE=true`. Скрипт
  проверил 71 закреплённый файл Sponza и записал хеши входов DXC.
  Профилирование кадров было выключено всю серию.
- Запуск в **00:03 CET**, после прекращения фоновой нагрузки на GPU. В
  шести секундных выборках перед запуском порог 0,35 % на отдельном движке
  GPU превышали только System и ChatGPT (максимум 0,662 %). Агрегированная
  загрузка NVIDIA измеряется другим счётчиком. `gpu.csv` хранит секундную
  телеметрию устройства от прогрева до конца серии около 00:14 CET.
  В ней нет разбивки по процессам.
- Один незачётный прогрев S1–S5 и три последовательных зачётных прохода
  в новых процессах. Для каждого процесса S1–S4 было 30 кадров прогрева и
  240 измеренных кадров, для S5 — 5 и 30. S1/S2 дают 239 интервалов между
  240 наблюдаемыми кадрами. См. [протокол бенчмарка](bench.md).

S1 и S2 уложились в `1000 / 60` мс по среднему и p95. Максимальный p95
составил 9,641 и 9,327 мс соответственно. Пик рабочего набора S1 составил
260,1 МиБ при бюджете 1024 МиБ. В R0.6 для S3–S5 нет абсолютных бюджетов
кадра и памяти. Разброс дополнительного шага GameHost в S1 составил 6,85 %.
Эта метрика находится за рамками критерия воспроизводимости S1.

S4/S5 статичны, поэтому игрового тика у них нет. GPU-тайминги по проходам
и дополнительные CPU-интервалы выключены для сопоставимости. S4 измеряет
262 961 треугольник с солнцем старого рендера. 256 точечных источников
есть в составе сцены, но их расчёт появится в R5. Принятого эталонного
изображения нет. В S5 измерены все 20 млн треугольников со старым развёрнутым
потоком вершин. Счётчики meshlets требуют R8. В таблице памяти приведён
пиковый рабочий набор процесса по данным ОС. Телеметрия GPU показывает
память всего устройства. Замер видеопамяти отдельного процесса и времени
от открытия редактора до первого кадра лежит за рамками протокола.

## Сравнение с R0.2

Данные о составе фикстур совпадают с [принятой серией R0.2](bench-r02-20261121.md).
Совпадают также GPU, драйвер, разрешение рендера, режим монитора и запрос
vsync. В R0.2 ещё не было профилирования и не записывался фактический режим
показа. Для каждого изменения сравнивается среднее из трёх средних или
среднее из трёх p95 соответственно. Плюс означает рост времени.

| Сцена | Изменение среднего / p95 кадра | Изменение среднего / p95 шага или тика | Изменение среднего / p95 рендера или отправки |
| --- | ---: | ---: | ---: |
| S1 | +0.00 % / +0.11 % | +0.43 % / +1.18 % | +0.67 % / +1.56 % |
| S2 | −0.14 % / −1.40 % | +0.28 % / +7.38 % | +0.86 % / −1.14 % |
| S3 | +0.41 % / +0.07 % | −3.65 % / −1.93 % | +0.64 % / +1.26 % |
| S4 | +2.51 % / +14.04 % | — | +2.02 % / +2.56 % |
| S5 | +2.09 % / +2.37 % | — | +2.70 % / +3.22 % |

Самое большое изменение p95 кадра у S4 (47,108 → 53,724 мс в среднем по
трём p95). Отдельные p95 составили 45,966–58,119 мс. Среднее трёх p95
шага S2 выросло с 3,679 до 3,950 мс, при этом сцена уложилась в бюджет
кадра. Рабочий набор S4 вырос с 397,5–399,9 до 425,6–427,8 МиБ. Это
наблюдаемые различия между снимками. Лимит разброса 5 % применяется к
заявленным средним внутри одной серии. Серия прошла эту проверку. Причина
наблюдаемых различий пока неизвестна.

Для [R1.1](product-roadmap.md#rebuild-r1) ориентир по текущему Core ECS —
**0,756 мс в среднем** по трём прогонам, p95 по прогонам **0,943–0,976 мс**.
Запросы, изменения, создание и удаление сущностей и снятие снимка нужно
сравнивать на той же фикстуре S3 с 2000 сущностями по восемь компонентов.
Одна пятая от округлённого среднего R0.6 составляет около **0,151 мс**.
Применяйте критерий пятикратного ускорения к сопоставимым замерам старого
и нового путей и проверяйте инварианты авторских данных. Приведённые выше
значения p95 шага S2 служат эталоном для R1.8.
