# R8.1. Эксперимент с mesh shaders на S5

[English](../r81-s5-meshlets.md) | [Русский](r81-s5-meshlets.md) | [Документация](../README.md)

R8.1 сравнивает две явные команды бенчмарка в сборке Editor из исходников.
Обе используют исходную сцену S5 из 40 участков с 20 000 000 индексированных
треугольников и 10 040 040 вершинами, камеру фикстуры и штатный граф Forward
при 1920×1080. В рабочем рендерере сохраняются действующие правила выбора
устройства, ABI шейдеров и отправки сцены.

- `S5-r24` строит существующую retained-сцену и использует R2.4 Hi-Z
  вместе с indexed indirect count. Команда требует активного пути R2.4 и
  записывает число команд после отбраковки. В её логическом устройстве Vulkan
  mesh shaders выключены.
- `S5-r81` строит meshlets в памяти через `meshopt` 0.6.2 с ограничением
  64 вершины и 124 треугольника на meshlet. Одна группа task запускает до
  32 групп mesh. Каждая группа mesh преобразует индексированные вершины,
  вычисляет плоские нормали и записывает исходные идентификаторы треугольников
  и объектов. В статическом прототипе task-шейдер запускает все meshlets.
  Счётчики отражают отправленную работу. Команда требует возможностей task
  и mesh из `VK_EXT_mesh_shader` и индексированных материалов Forward.

Стоимость построения включает кластеризацию, восстановление исходного
порядка вершин в пределах треугольника и упаковку для загрузки. Оба пути
загружают сцену один раз и рисуют из буферов в памяти устройства. В область
эксперимента входят измерения статического пути. Хранение meshlets в ассетах,
проверка видимости отдельных meshlets, кэширование импорта, LOD и порог
60 FPS этапа R8.3 относятся к следующим этапам.

## Воспроизведение

Используй эталонный Windows GPU без конкурирующей нагрузки и закреплённую
в проекте версию DXC. Возьми исполняемый файл из результата bench-сборки
и сохрани путь к этому артефакту в отчёте.

```powershell
cargo build --locked --release -p module-engine-editor --features bench
python -B scripts/bench_r81.py --exe <bench-exe> --output outputs/r81/series
```

Сравнение сначала считывает оба изображения 1080p. Оно проверяет устройство,
размер, совпадение всех счётчиков RenderStats, наличие пикселей с геометрией
и принадлежность каждого пикселя одному и тому же объекту. При различии
triangle ID проверка требует, чтобы два исходных треугольника этого
объекта имели общее ребро, а их положительные глубины различались не более
чем на один шаг `f32`. Центр пикселя должен отстоять от проекции ребра
не более чем на шаг субпиксельной сетки GPU. Сырые нормали и цвета Forward
без текстур должны совпадать с расчётом для соответствующих граней с
точностью 1e-5. Проверка допускает только однозначные ID и до двух таких
пикселей в 1080p, с абсолютным отклонением RGBA8 до 4 на канал. Во всех
остальных пикселях допускается до 2 на канал. В отчёте сохраняются обе PNG,
общий максимум, число различий на общих рёбрах, а также глубина, нормаль,
цвет и исходные ID в пикселе с наибольшим отклонением. Для диагностики команда
`R81-visibility-no-fxaa` отключает FXAA в обоих путях. Зачётный замер
требует полного графа Forward и запускает пять пар нативных процессов,
меняя порядок путей в соседних парах. Каждый процесс прогревается пять
кадров и записывает 30 нативных кадров с GPU timestamps, без переноса
пикселей на CPU, с выключенным vsync и режимом представления Immediate.
Оба пути должны сообщить одинаковые параметры представления, сцены и
устройства и подтвердить ожидаемый способ отправки геометрии в каждом
кадре. Отчёт содержит медианы средних и p95 по прогонам, допуск по разбросу
R2.4, пиковый рабочий набор процесса, счётчики аллокатора рендерера,
разовую подготовку и загрузку геометрии и число команд рисования. Счётчики
аллокатора объединяют учитываемые им пулы. Пик общего расхода VRAM отдельно
не измеряется.

Отдельно запусти проверку изображений в debug-сборке с активными Khronos
validation layer и проверкой синхронизации через
`--bench-scene R81-visibility <new-output>`. Сохрани журналы компилятора и
процессов и хеши исходников и сборок. См. [проверки R2.4](bench.md#r24-culling-checks),
[возможности и ограничения mesh shaders](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_mesh_shader.html)
и [атрибуты SPIR-V в DXC](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/SPIR-V.rst).

## Результат замера — 25 ноября 2026

В фиксированном ракурсе S5 путь task/mesh сократил среднее время
графа GPU-производителя на **45,94%**, p95 — на **42,56%**. В таблице
медианы статистик по пяти парам, по 150 зачётных кадров на каждый путь.
Использовались штатный Forward и нативный мост WGPU/DX12 при 1920×1080
с режимом представления Immediate, выключенным vsync и GPU timestamps
на каждом зачётном кадре. Перенос пикселей на CPU в серии составил 0 байт.

| Метрика | R2.4 Hi-Z и indexed indirect count | R8.1 task/mesh |
| --- | ---: | ---: |
| Граф GPU, среднее / p95, мс | 4,552 / 4,977 | 2,461 / 2,858 |
| Проход геометрии на GPU, среднее / p95, мс | 2,560 / 3,012 | 2,067 / 2,452 |
| Интервал по наблюдениям окна, среднее / p95, мс | 6,001 / 6,528 | 3,590 / 4,201 |
| Отправка на CPU, среднее / p95, мс | 0,324 / 0,401 | 0,211 / 0,289 |
| Пиковый рабочий набор процесса, МиБ | 2 391,8 | 1 560,4 |
| Аллокатор производителя, занято / зарезервировано, МиБ | 725,2 / 896,0 | 593,0 / 832,0 |
| Первая загрузка геометрии, МиБ | 426,1 | 398,9 |
| От начала первой отправки до наблюдаемого завершения, мс | 1 237,0 | 259,7 |
| Кластеризация и упаковка meshlets, мс | — | 15 926,2 |
| Выделение памяти и подготовка загрузки meshlets, мс | — | 36,4 |

Интервал первого завершения отсчитывается после подготовки сцены и
устройства. Кластеризация и упаковка в него не входят. p95 отправки с
CPU попал в допуск по разбросу. Два оконных интервала mesh-пути
превысили 16,67 мс и составили 20,920 и 20,726 мс. Все 150 интервалов
R2.4 были короче 16,67 мс, максимальный составил 7,173 мс.

Предпроход глубины R2.4 обработал все 40 участков, и Hi-Z сохранил все 40.
Среднее время отбраковки составило 1,824 мс. Эта стоимость входит в
разницу по всему графу. Среднее время самого прохода геометрии Forward
сократилось на 19,27%. Прототип отправил 6 510 групп task на 208 305
meshlets и все 20 миллионов исходных треугольников. Отбраковка отдельных
meshlets была выключена.

Оба пути работали на одной RTX 4080 SUPER (`10de:2702`, 16 376 МиБ),
драйвер 617.42, Vulkan 1.4.351, Windows 11 build 26300. Устройство сообщило
`VK_EXT_mesh_shader` ревизии 1, обе возможности task/mesh и поддержку
mesh shader queries. Рабочие группы task и mesh поддерживали по 128
вызовов с предпочтительным размером 32. Предел отправки по X и суммарный
предел составляли 4 194 304 для обеих стадий. Выход mesh ограничен
256 вершинами, 256 примитивами и 32 768 байтами. Предел payload для task
составлял 16 384 байта. Максимальный диапазон storage buffer —
4 294 967 295 байт, на графической очереди было 64 значимых бита
timestamp с периодом 1 нс. В логическом устройстве R2.4 mesh extension
выключен.

Release-проверка изображения подтвердила совпадение каждого object ID и
всех счётчиков RenderStats. RGBA8 различался в семи пикселях. Максимум 3
пришёлся на одно подтверждённое общее ребро исходных треугольников, в
остальных пикселях максимум составил 1. Прежний строгий предел 2 для
всего изображения на этом ребре был превышен. PNG из Debug побайтно
совпали с соответствующими PNG Release. На обоих устройствах Debug
подтверждена активная Khronos synchronization validation, счётчики
предупреждений и ошибок при завершении равны нулю. На Windows прошли
оба адресных CPU-теста и строгий адресный Clippy.

SHA-256 Editor Release и Debug соответственно
`5a38bfcf1a04b88baaa1d0bec3cba5775b4a84e5744c6099e7c5ee8a71d98291`
и `c836e56d9ce35ec92ce4ffd3d2db7b91d2c5d9d46c90fbcc695f3dcc5f7af73b`.
Очередь сохранила обе сборки, исходные журналы и отсчёты, а также отказы
по прежнему критерию. [Реализация и ревью](https://github.com/ModuleEngine/ModuleEngine/pull/56)

Замер даёт основание продолжить эксперименты уровня B с предварительно
подготовленной геометрией. Измеренная стоимость построения слишком велика
для штатной загрузки сцены. Сохраняем действующий рабочий рендерер и путь
уровня A. Результат охватывает одну камеру на одном Windows GPU и не
гарантирует время кадра на других ракурсах, устройствах только уровня A
или Linux GPU.
