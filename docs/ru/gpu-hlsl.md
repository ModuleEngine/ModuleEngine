# Vulkan и Custom HLSL

[English](../gpu-hlsl.md) | [Русский](gpu-hlsl.md) | [Документация](README.md)

Renderer исполняет raster и compute проходы на Vulkan. В редакторе HLSL компилируется DXC в SPIR-V; renderer создаёт pipelines, изображения и барьеры. При экспорте Player шейдеры компилируются заранее. Два встроенных пути различаются реальной последовательностью GPU-работы.

| Проход | Вход/результат |
| --- | --- |
| gpu.forward | Scene3D → цвет HDR, нормали в мировых координатах, линейная глубина камеры. |
| gpu.gbuffer | Scene3D → линейное альбедо, нормали, глубина. |
| gpu.deferred | G-buffer → освещение HDR. |
| gpu.depth_normal | Scene3D → нормали/глубина. |
| gpu.ssao | HDR + normals/depth → HDR с ambient occlusion. |
| gpu.tonemap | HDR → linear LDR; режимы ACES/Reinhard, exposure. |
| gpu.fxaa | Linear LDR → Linear LDR, spatial AA текущего кадра. |
| gpu.color_encode | Линейный LDR → rgba8unorm/srgb_display. |
| gpu.custom | Собственный raster/compute проход с params.manifest и source_id. |

`gpu.ssao` восстанавливает мировые позиции относительно камеры из линейной
глубины камеры и общего camera basis. Сосед вносит вклад только выше касательной
плоскости принимающей поверхности и в пределах distance falloff; свободная
наклонная плоскость не должна затенять сама себя. Восемь экранных смещений и
strength остаются ограниченным встроенным приближением, а не полной физической
моделью окклюзии. См. [регрессию плоскости/ореолов и поставку](release-042-ssao-verification.md).

## Редактирование в Engine

Выберите «GPU Forward» или «GPU Deferred», затем откройте вложенный граф renderer двойным щелчком. Выберите проход: инспектор показывает его параметры и контракты ресурсов. **Replace with editable Custom HLSL** копирует поставляемый текст шейдера и manifest в проект, сохраняя ID прохода и его внешние связи.

Во вкладке «HLSL» редактируйте текст и нажмите **Apply HLSL**. Неверный кандидат остаётся в проекте с диагностикой; предыдущая рабочая конфигурация сохраняется. Изменять ресурсы, bindings и точки входа нужно согласованно с manifest.

Самостоятельные шаблоны находятся в assets/gpu/custom_compute.hlsl, custom_raster.hlsl и custom_fullscreen.hlsl. Они доступны как обычные исходники.

## Manifest прохода

Пример params для HDR compute-фильтра:

~~~json
{
  "source_id": "my_filter",
  "gain": 1.0,
  "manifest": {
    "stage": "compute",
    "entry": "main",
    "workgroup": [8, 8, 1],
    "parameters": ["gain"],
    "inputs": [{
      "name": "color", "format": "rgba32float",
      "semantic": "hdr_linear", "extent": "viewport",
      "samples": 1, "access": "sampled_read"
    }],
    "outputs": [{
      "name": "color", "format": "rgba32float",
      "semantic": "hdr_linear", "extent": "viewport",
      "samples": 1, "access": "storage_write"
    }]
  }
}
~~~

source_id указывает на shader_sources. stage — compute или raster. Для raster raster_mode выбирает scene/fullscreen; entry задаёт fragment entry, vertex_entry — необязательную пользовательскую vertex entry. scene raster принимает ровно один Scene3D, fullscreen/compute его не принимают.

ResourceSpec содержит name, format, semantic, extent, samples, access. Форматы изображений: rgba32float, r32float, rgba8unorm. semantics встроенных проходов: hdr_linear, ldr_linear, albedo_linear, world_normals, camera_linear_depth, srgb_display; сцена имеет format:scene/semantic:scene3d. Входные изображения используют sampled_read, выход raster — color_write, compute — storage_write. Совместимость требует совпадения формата, semantic, extent и samples.

Неизвестные поля manifest/ResourceSpec отклоняются. params прохода допускает только объявленные параметры, enabled:bool и служебные source_id/manifest у Custom. До 16 scalar-параметров; порядок parameters определяет размещение значений в push constants. Встроенный tonemap отдельно поддерживает строковый mode.

## HLSL ABI

Descriptor set 0: сначала входные bindings в порядке inputs, затем выходные compute bindings в порядке outputs. Texture2D<float> и Texture2D<float4> читаются через Load; sampler/buffer bindings в этом manifest пока отсутствуют. У storage image требуется точный атрибут vk::image_format, например rgba32f. Reflection проверяет скомпилированные image type, bindings, storage format и LocalSize.

Push constants — 128 байт: четыре float4 камеры и четыре float4 параметров. Используйте поставляемое объявление [[vk::push_constant]] ConstantBuffer<Config>; параметры занимают values, например первый scalar — values[0].x.

Compute workgroup должен совпадать с numthreads в SPIR-V, z=1, произведение размеров — от 1 до 256. Проверяйте границы изображения до Store. Для scene vertex ABI: position float3, normal float3, color float4, ids float2, UV float2, atlasRect float4, locations 0–5, stride 72 байта. Первые 48 байт сохраняют прежнее расположение данных: существующий Custom шейдер может использовать только locations 0–3. Пример vertex/fragment пары находится в custom_raster.hlsl.

Растровый проход Scene с `scene_materials: true` на пути совместимости использует исходный ABI материалов. После явно объявленных входов в set 0 добавляется одно читаемое изображение атласа базового цвета из `SceneSnapshot`. UV (location 4) интерполируются с учётом перспективы. Неинтерполируемый atlasRect (location 5) задаёт начало и размер в пикселях для `Texture2D.Load`. Совместимые встроенные шейдеры явно декодируют sRGB. Depth/normal и другие проходы Custom получают ресурсы материалов при явном объявлении. [Подробности импорта](content.md).

Forward и G-buffer также объявляют `bindless_materials: true`. Built-in → Custom копирует весь manifest и обе ветви HLSL. Для индексируемого fragment-шейдера компилятор задаёт `MODULE_ENGINE_BINDLESS_MATERIALS`. В set 1 находятся `Texture2D<float4>[]` в binding 0, `SamplerState` в binding 1 и `StructuredBuffer<uint>` в binding 2. В буфере индексов по одной строке на элемент сцены. Для обращения к строке прибавьте `ids.y - 1`, где `ids.y` не интерполируется и начинается с единицы, к `asuint(values[3].w)`. Для сохранённого индекса используйте `NonUniformResourceIndex`, а для чтения используйте `Sample` с UV без взятия дробной части, чтобы сохранить производные. Представление sRGB декодирует цвет. Проход с двумя вариантами принимает только вход Scene3D и до 15 скалярных параметров. Push constants по-прежнему занимают 128 байт, формат вершин сохраняется.

[Штатный путь со сценой в памяти GPU](hardware-tiers.md#r23-scene) использует
внутренний вершинный шейдер со storage buffer в set 0, bindings 1–4. В них
лежат координаты с UV, индексы, инстансы и цвета. Шейдер выдаёт штатные
интерполируемые данные, включая существующие ID треугольников и объектов.
Интерфейс индексируемого фрагментного шейдера в set 1 сохранён, а индексы
изображений R2.2 читаются из постоянного буфера сцены. Диапазон отрисовки
использует `values[3].y/z` как беззнаковые битовые значения, чтобы восстановить
ID объекта и треугольника в текущем опубликованном порядке. База строки
`values[3].w` сопоставляет опубликованный ID объекта с постоянным слотом
материала. При переводе штатного
прохода в Custom используется опубликованный интерфейс развёрнутых вершин.
Экспорт Player сохраняет внутреннюю вершинную стадию вместе со штатной
стадией совместимости.

Экспорт сохраняет оба fragment-варианта. Существующий проход Custom, объявляющий только `scene_materials`, сохраняет привязку атласа и все 16 параметров на любом устройстве. [Выбор пути на устройстве](hardware-tiers.md#r22-materials).

Inline HLSL ищет буквальные #include в assets/gpu выбранного пакета, затем в корне этого пакета. Для вложенного quoted include первым ищется каталог содержащего файла; angle include использует assets/gpu→root. JSON из отдельного Full/Team пакета использует его marker/resource root. Самостоятельный JSON без marker не делает свой каталог новым compiler root; source_id не является путём. Экспорт рекурсивно собирает эти зависимости. Содержимое разрешённых include читается перед выбором pipeline и входит в fingerprint: изменение header инвалидирует compile/pipeline cache даже при неизменном inline тексте. Это проверено изменением реальных GPU-пикселей. Макрос вместо имени include отклоняется при сборе зависимостей, чтобы экспорт не терял неизвестные файлы.

Готовые ACES/Reinhard и FXAA/off можно открыть автору Project как разрешённые варианты; Team не изменяет граф/HLSL. DLAA/SMAA пока отсутствуют.

## Заранее скомпилированный Player и кеши

`precompile_graph_at(graph, sources, source_root, destination)` компилирует и проверяет все стадии выбранного графа, включая vertex, и пишет `destination/.spirv`. При наличии `.spirv` renderer использует только эти артефакты: DXC не запускается и отката к инструментам автора нет. Отсутствующий/повреждённый shader приводит к диагностике и требует повторного экспорта. Include-файлы сохраняются в пакете, потому что их содержимое проверяется тем же fingerprint. Для других разрешённых графов экспортёр вызывает precompile отдельно в тот же каталог.

В редакторе устойчивый `.work/shader-cache` повторно использует SPIR-V по исходнику, entry/profile и содержимому include closure. Полный артефакт публикуется переименованием временного файла; незавершённый результат не должен читаться параллельным компилятором.

Корневой HLSL-текст имеет одинаковую идентичность шейдера при окончаниях строк LF, CRLF или смешанных LF/CRLF. Прямой ключ исходника и корневая текстовая часть dependency fingerprint приводят CRLF к LF; текст с LF сохраняет прежний ключ. Компиляция и авторские файлы сохраняют исходные байты. Одиночный CR, другие изменения исходника, entry/profile и разрешённые пути include по-прежнему влияют на идентичность; include-файлы учитываются точными байтами, включая окончания строк. Это предотвращает расхождение exporter и отдельно собранного Player только из-за разных Windows-окончаний строк во встроенном корневом тексте. Хеш является внутренним ключом кэша, а не стабильным внешним ABI.

Ранний самостоятельный пакет Player сохраняет свой executable и pinned-артефакты без изменений. Если пересобранный runtime ожидает иной ключ из старого sealed-пакета, выполните повторный экспорт согласованной текущей парой Editor/Player; не переименовывайте `.spirv` и не ослабляйте pins пакета. Установка Team со старым выбранным вариантом Player требует новой штатной поставки Team, собранной из согласованных Full-исходников. Отсутствующие артефакты по-прежнему приводят к отказу без запуска DXC или отката к инструментам автора.

Backend сохраняет изображения проходов и vertex buffer пути совместимости между кадрами одинаковой конфигурации/размера; явный CPU render также переиспользует readback buffer. GPU material atlas загружается при изменении набора декодированных текстур и используется повторно. Native-показ возвращает GPU-аренду без CPU RGBA-пикселей. Явный CPU render с `set_detailed_stats(false)` читает лишь RGBA8 без depth, normals и цветовых ID. В таком режиме ownership/coverage counts не измеряются; ноль не означает невидимую сцену. Submitted counts остаются доступны.

Идентичность ресурсов включает ID проходов и их выходов, а не только набор pipelines: удаление AO и добавление такого же прохода с другим ID требует нового набора изображений. Иначе повторно использованный `ao.color` не соответствует новому `pass_id.color`. GPU-план проверяется отдельно от кеша изображений; контракты настроек проверяются по metadata без повторного чтения шейдеров. Для неизменённого кадра план переиспользуется, а внешние includes проверяются с интервалом 250 мс; явная подготовка всегда читает актуальные includes.

Неверный внешний include сохраняет предыдущий рабочий GPU-план и возвращает диагностику; окно сохраняет последний успешный кадр. Повторные кадры используют сохранённую ошибку, а после интервала проверяются bytes зависимостей. Неизменившийся неудачный набор не запускает DXC снова; исправление или восстановление файла разрешает следующую попытку без редактирования inline HLSL. Такой же контроль зависимостей позволяет повторить отклонённую фоновую подготовку Game/Scene. Явная `prepare` выполняет свежую попытку независимо от этого ограничения.

Временные HLSL/SPIR-V файлы удаляются и при отказе компиляции. Перед публикацией SPIR-V повторно проверяется revision зависимостей; сохранение include во время компиляции отклоняет устаревший результат. Перед добавлением нового pipeline проверяется тот же fingerprint прохода, чтобы смешанные стадии не записались под прежним ключом.

В явном CPU/диагностическом пути readback buffer предпочитает память `HOST_VISIBLE | HOST_COHERENT | HOST_CACHED`. Просто первая host-visible память дискретной видеокарты может оказаться медленно читаемым CPU BAR mapping. Если cached coherent тип недоступен, backend использует прежний compatible host-visible coherent тип. Барьер transfer→host и завершение очереди сохраняются.

Renderer отдельно измеряется командой `cargo run --locked --release -p module-engine-vulkan --example gpu_benchmark`: 20 импортированных текстурированных моделей, полная стандартная цепочка Forward/SSAO/tonemap/FXAA/encoding, 1920×1080, 10 кадров прогрева и 120 измеряемых кадров. На RTX 4080 SUPER после исправления readback memory получено в среднем 3.11 ms, p95 3.98 ms. Это диагностический замер renderer с CPU readback, без игровых подсистем и вывода egui; критерию готового Player соответствует отдельный полный замер. JSON пишется в `.work/gpu-benchmark.json`.

## Показ кадров на GPU

Обычный нативный вывод Vulkan публикует непрозрачный объект аренды GPU-кадра вместо пикселей CPU. На Windows отдельный производитель Vulkan передаёт изображение в WGPU/DX12 через общие ресурсы D3D12; на Linux отдельные устройства Vulkan используют выделенную память OPAQUE_FD с точным совпадением UUID устройства и драйвера. Мост интерфейса копирует RGBA8 и умножает цвет на альфа-канал на GPU в собственную текстуру `Rgba8Unorm`, сохраняя округление байтов прежнего преобразования egui без декодирования sRGB. Обычный показ не читает пиксели на CPU и не загружает их обратно. Неподдерживаемое взаимодействие графических API или его ошибка сохраняют последнее рабочее изображение и сообщают диагностику без молчаливого перехода на передачу через CPU.

Слой устройства Vulkan допускает до двух GPU-отправок на [уровне A с поддержкой timeline](hardware-tiers.md#r21-device) и одну на пути совместимости. Обычные Player и Host редактора ведут по одной незавершённой транзакции кадра. Четыре арендуемых выходных изображения ограничивают повторное использование производителем и потребителем независимо от слотов команд. После приёма `render_presented` возвращает `RenderSubmission::Pending(ticket)`. `poll_presented(ticket)` проверяет завершение без ожидания и публикует этот запрос максимум один раз. `Busy` не принимает работу. `Ready(Frame)` поддерживает немедленный вывод CPU/software. До завершения действуют предыдущие изображение, идентичность, камера и происхождение. Слот удерживает ресурсы команд, атлас и ссылки на pipelines до завершения их использования GPU. GUI удерживает аренду общего изображения до фактического окончания работы потребителя на GPU, в том числе при свёрнутом окне. Явный CPU-рендер, диагностика Glow и PNG-захват могут синхронно ждать чтения. Конфликтующий CPU-рендер отклоняется, пока нативная работа не завершена.

Допустимый кандидат graph/HLSL может компилироваться и прогревать кэши при ожидающем запросе, не выбирая себя для этого запроса. Отправленные команды удерживают все используемые pipeline/layout и ресурсы сцены/атласа/размеров до завершения; недопустимый кандидат сохраняет этот запрос и принятую обёртку. Счётчики отправленных и завершённых GPU-кадров различаются.

Отмена отбрасывает публикацию и удерживает работу до подтверждения её завершения на GPU. При уничтожении рендера занятые слоты переходят в общую очередь удаления. Она опрашивает последнее значение timeline или fence пути совместимости вне потока рендера. При выходе приложения очередь обрабатывается после остановки владельцев рендера. `finish_gpu_retirements` сообщает об освобождении ресурсов потребителя и вложенных счётчиках производителя registered/joined/completed/unconfirmed/failed. Таймаут (30 с на производителя в очереди), ошибка устройства, panic или отказ запуска рабочего потока сообщаются как ошибка и сохраняют неподтверждённые ресурсы и удержание устройства. На Linux потребитель сохраняет действующий карантин при ошибке освобождения владения.

Новые асинхронные исходники требуют отдельно привязанных проверок и независимого вывода в [асинхронном отчёте](gpu-async-20261018.md); прохождение отдельных текущих критериев не означает отсутствие ухудшения или итоговую приёмку. [Исторический GPU-отчёт](gpu-presentation-20261018.md) сохраняет результаты Windows source15/Linux source11 и прежние неудачи, включая открытый на тот момент cold-критерий. [Продолжение от 18 октября](p0-continuation-20261018.md) отдельно фиксирует последующий обычный cold PASS 40,906/39,9128549 с, Windows22/16 и WSL Linux23/16 и ограниченные native/package/lifecycle проверки своих исходников. Эти снимки не проверяют новую асинхронную реализацию и не подтверждают аппаратный Linux, реальную потерю устройства или физический scanout.

## Ограничения и требования

Проверка исходников Full требует `crates/render-vulkan/src/retirement.rs`. Пакет Full, в inventory исходников которого отсутствует этот модуль, должен отклоняться до включения редактирования Engine.

Нужен Vulkan 1.3, dynamicRendering, очередь с graphics+compute, host-visible coherent память и device-local изображения. Форматы RGBA32_SFLOAT/R32_SFLOAT/RGBA8_UNORM должны поддерживать используемые color attachment/sample/storage/transfer операции; D32_SFLOAT — depth attachment/transfer src. Наличие vulkan-1.dll не доказывает возможности адаптера: их проверяет реальное создание backend.

Buffer/Image получают RAII-владельца сразу после создания первого Vulkan handle. Отказ выбора/выделения памяти, binding или image view освобождает уже созданные части. Native regression вводит ошибки на промежуточных стадиях, проверяет баланс handles/device memory и последующий успешный GPU-кадр; она не требует намеренно исчерпывать видеопамять.

Изображения viewport однослойные, samples=1; максимум 4096 по каждой оси и 4 млн пикселей. MSAA/resolve и temporal AA отложены. Swapchain игрового renderer отсутствует. Обычный native output использует общие GPU-изображения; явный CPU/диагностический output синхронно читает пиксели.

Clear/copy команды адресуют pass_id.output_name и выполняются после producer в порядке отправки. Неверный ресурс, несовместимый copy или запись после первого consumer отклоняются. enabled override переносимого Rust имеет приоритет над params.enabled; выключение допустимо только при совместимом одиночном image bypass.

Для встроенной геометрии renderer читает видимые ID и измеряет ownership. У произвольного custom scene шейдера доступны submitted triangles и coverage; нулевые ownership counts означают отсутствие такого измерения, а не доказательство отсутствия видимой геометрии.
