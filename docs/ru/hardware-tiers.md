# R0.4 — Аппаратные уровни Vulkan

[English](../hardware-tiers.md) | [Русский](hardware-tiers.md) | [Документация](README.md)

**21 ноября 2026.** Настольная **GeForce GTX 1660 SUPER (6 ГБ)** — кандидат
в минимальную карту уровня A для Player на Windows. В R0.4 проверена одна
конфигурация, эталонная система Windows с **GeForce RTX 4080 SUPER**.
Требования уровней относятся к [перестройке](product-roadmap.md#rebuild-r0).
Снимок R0.4 сделан на исходниках
`b50e76d20006598cae423bc8e8d3a78f8007d147`.

Каждый путь запрашивает и включает используемые им биты. Сам по себе
`descriptorIndexing` не включает отдельные возможности индексации. Версия
Vulkan API сама по себе не подтверждает необязательные биты индексации
и расширения B/C. Режимы привязки и лимиты дескрипторов проверяются в R2.2.
Например, частично
заполненные привязки требуют `descriptorBindingPartiallyBound`, переменный
размер привязки — `descriptorBindingVariableDescriptorCount`, а неоднородная
индексация массивов storage-буферов — `shaderStorageBufferArrayNonUniformIndexing`.
Обновление после привязки требует бит для соответствующего типа дескриптора,
например `descriptorBindingSampledImageUpdateAfterBind`. Для R2.1 также
проверяется `timelineSemaphore`, а для групп непрямых команд в R2.4 —
`drawIndirectCount`, `multiDrawIndirect` и `maxDrawIndirectCount`.
Эти проверки относятся к использующим их функциям.
См. спецификации Khronos для [возможностей Vulkan 1.2](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceVulkan12Features.html),
[Vulkan 1.3](https://docs.vulkan.org/refpages/latest/refpages/source/VK_VERSION_1_3.html),
[mesh shaders](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_mesh_shader.html),
[структур ускорения](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_acceleration_structure.html),
[лучевых запросов](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_ray_query.html)
и [конвейеров трассировки](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_ray_tracing_pipeline.html).

## Что использует текущий Player

[Производитель кадров Vulkan](../../crates/render-vulkan/src/vulkan.rs)
запрашивает Vulkan 1.3 и очередь graphics + compute с dynamic rendering.
Без окна он предпочитает подходящий дискретный адаптер. Для окна очередь
должна поддерживать показ на нативную поверхность, а устройство —
`VK_KHR_swapchain`. В Windows и Linux окно и производители графа используют
одно логическое устройство. Форматы SDR, режимы показа и сроки жизни
изображений описаны в [контракте Player](player.md). [Исполнение графа](gpu-hlsl.md#r25-graph)
проверяет поддержку synchronization2 и timeline отдельно от двухслотового
пути с аллокатором уровня A.

<a id="r21-device"></a>

## Слой устройства R2.1 и проверка

Производитель проверяет отдельные возможности A, B и C на выбранном
адаптере. B и C независимы. Renderer включает те биты, которые использует.
На уровне A с `timelineSemaphore` включаются два слота команд и
дескрипторов, synchronization2 и gpu-allocator. Другие адаптеры, которые
проходят существующие проверки Vulkan 1.3 и dynamic rendering, используют
один слот с fence и отдельными выделениями памяти. Индексация дескрипторов,
адреса буферов, mesh shaders и лучи на этом этапе отражаются в возможностях.

Аллокатор выдаёт участки памяти для буферов и изображений производителя
и учитывает обязательные dedicated allocation. Импортируемая внешняя
память выделяется отдельно. Запись вершин и явное диагностическое чтение
используют когерентную отображённую память. Новые атласы проходят через
отображённое staging-кольцо. Последнее значение завершения графических
команд определяет повторное использование диапазонов и срок жизни
заменённых staging-буферов. Производитель загружает атлас целиком в
выделенном семействе transfer, когда оно доступно, освобождает владение
изображением там и принимает в графической очереди после зависимости
по timeline на GPU. Иначе копирование записывается в графический командный
буфер. Слоты удерживают GPU-ресурсы и ссылки на pipelines до подтверждения
завершения. Общий поток очереди удаления опрашивает отсоединённые занятые
слоты. Обычный нативный производитель возвращает `Busy`, если слоты или
арендуемые выходные изображения заняты. Явное диагностическое чтение может
ждать свою отправку.

Запускайте на свободном рабочем столе Windows с DXC и установленным или
распакованным локально слоем валидации Khronos. Укажите в `VK_LAYER_PATH`
каталог манифеста слоя. Выполните сцены последовательно без конкурирующих
сборок и перекрытия окна замера. Переопределение Cargo включает диагностику
Vulkan в crate Vulkan оптимизированного Editor.


```powershell
$env:VK_LAYER_PATH = (Resolve-Path 'work/verification/r21/layer').Path
$env:VK_LOADER_DEBUG = 'layer'
$env:VK_LAYER_ENABLES = 'VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT'
$env:MODULE_ENGINE_VULKAN_TRACE = '1'
$env:MODULE_ENGINE_BENCHMARK_ARM = 'automatic'
$env:MODULE_ENGINE_BENCHMARK_FRAMES = '240'
$env:MODULE_ENGINE_BENCHMARK_PROFILING = 'off'
$env:MODULE_ENGINE_GUI_VSYNC = 'off'
cargo --config 'profile.release.package.module-engine-vulkan.debug-assertions=true' build --locked --release --features bench -p module-engine-editor
if ($LASTEXITCODE) { throw 'Editor build failed' }
$out = New-Item -ItemType Directory "outputs/r21-repeat-$(Get-Date -Format yyyyMMdd-HHmmss)"
$exe = (Resolve-Path 'target/release/module-engine-editor.exe').Path
foreach ($scene in 'S1','S2','S3') {
    & $exe --bench-scene $scene (Join-Path $out.FullName $scene) *> (Join-Path $out.FullName "$scene.log")
    if ($LASTEXITCODE) { throw "$scene failed" }
}
git rev-parse HEAD
Get-FileHash $exe
```

Журнал загрузчика должен показывать подключение `VK_LAYER_KHRONOS_validation`.
Каждая сводка производителя должна содержать `validation=active` и
`errors=0`, включая завершение приложения. Проверьте в JSON каждой сцены
240 измеренных кадров и нативный вывод без чтения пикселей на CPU. События
`Vulkan frame begin`, `submit`, `complete` и `wait` в журнале содержат
производителя и порядковый номер отправки. На пути timeline этот номер
равен значению семафора. `previous` — прежнее использование слота,
`completed` — значение графического timeline на начало записи CPU.
Прежний кадр должен завершиться до повторного использования слота. На пути
timeline S3 должен достигнуть двух активных ticket. Для обычных S1–S3
не должно быть событий `Vulkan frame wait`. Явная диагностика помечает
синхронное ожидание как `reason=diagnostic`. Событие `Vulkan transfer submit`
фиксирует сигнал загрузки, если доступно выделенное семейство.
Локальные данные проверки лежат в `outputs/r21/`. Отдельно записаны
[замеры прототипа S3](decisions.md#r21-device-prototype). Ограничения
аппаратной квалификации указаны ниже.

<a id="r22-materials"></a>

## R2.2 — Индексируемые материалы

Для индексируемого пути нужны timeline и аллокатор R2.1,
`shaderSampledImageArrayNonUniformIndexing`, `runtimeDescriptorArray` и
`samplerAnisotropy`. Рендерер проверяет обычные лимиты на 1 024 дескриптора
читаемых изображений на fragment-стадию и набор, общий лимит ресурсов стадии,
место для sampler и двух storage buffer, а также возможность привязать два набора.
Формат `R8G8B8A8_SRGB` с optimal tiling должен поддерживать чтение,
линейную фильтрацию, перенос и blit. Sampler повторяет UV, линейно фильтрует
тексели и уровни mip и использует анизотропию до 16× в рамках лимита устройства.

Набор материалов содержит 1 023 слота для текстур и белую текстуру по
умолчанию. Для BC-цепочек R5.1 также нужны `textureCompressionBC` и поддержка
чтения, линейной фильтрации и записи переносом при optimal tiling для форматов
`BC7_SRGB_BLOCK`, `BC7_UNORM_BLOCK` и `BC5_UNORM_BLOCK`. При отсутствии
пригодной сжатой цепочки очередь graphics загружает RGBA8 и строит остальные
уровни линейными blit в sRGB или линейном изображении в зависимости от карты.
Для каждого изображения действует собственный лимит размера устройства.
Новый набор переиспользует неизменившиеся изображения. На пути со снимками каждый набор хранит свой
буфер соответствий объектов и индексов текстур. Отправленный кадр
удерживает набор, изображения и staging до завершения работы GPU. Набор заполняется перед отправкой и остаётся
неизменяемым, поэтому путь обходится без update-after-bind, partially-bound
и variable-count.

Атлас применяется на устройствах, где индексируемый путь недоступен, в
Custom-проходах с прежним ABI материалов и при превышении ёмкости таблицы
дескрипторов. Атлас должен укладываться в 8192 пикселя по каждой оси. См.
[ABI проходов](gpu-hlsl.md#hlsl-abi) и
[воспроизведение](bench.md#r22-material-checks).

<a id="r23-scene"></a>

## R2.3 — Сцена в памяти GPU

Сцена в памяти GPU требует индексируемых материалов, `multiDrawIndirect`,
`drawIndirectFirstInstance`, места для четырёх storage buffer на стадии
вершинного шейдера и пяти дескрипторов storage buffer в pipeline layout.
Подходящее устройство сообщает `resident_scene: true` в возможностях Vulkan.
Сохранённая сцена идёт по этому пути, если её активные растровые проходы
сцены — штатные Forward, G-buffer или Depth/Normal, данные укладываются
в лимиты буферов и материалов, а представление трансформаций не переполняется. Прямые снимки, проходы Custom для сцены и
устройства на пути совместимости используют прежний поток вершин.
Полноэкранные и вычислительные проходы Custom могут выполняться после
отрисовки сцены из памяти GPU.

Vulkan хранит индексированные данные мешей в общем пуле на протяжении жизни
устройства. Вершинный шейдер читает локальные координаты, UV и индексы
треугольников, применяет трансформацию инстанса и вычисляет нормаль грани в
мировых координатах. Постоянный буфер инстансов хранит трансформации и индексы
строк материалов. Постоянные строки материалов хранят итоговый цвет и индекс
изображения R2.2. Рендер сохраняет позиции неизменившихся текстур при создании
нового набора дескрипторов. При росте пула заполненная часть копируется на GPU,
а CPU передаёт только новые данные мешей. Примитив сохраняет свой слот GPU
по стабильному ID объекта и порядковому номеру внутри него, пока он есть
в сцене. При удалении слот исключается из упорядоченных диапазонов
отрисовки. Вставка может занять свободный слот, а замена меша обновляет
строки этого объекта. При росте буфера неизменившиеся области копируются
на GPU.

Диапазоны сохраняют опубликованный порядок и ID. Каждый диапазон включает
последовательные физические слоты с одинаковыми разницами между физическими
и опубликованными ID объектов и треугольников. Три константы штатного
прохода восстанавливают опубликованные ID и направляют чтение материалов
в физические слоты. При структурной правке CPU по-прежнему проходит
упорядоченный список сцены, чтобы собрать диапазоны. Частые правки могут
разбить диапазоны и увеличить число косвенных команд на пути R2.3. Эти границы измеряет
[структурный бенчмарк](bench.md#r23-scene-checks).

Оба слота кадра используют одни и те же постоянные буферы. Барьеры в очереди
завершают предыдущие чтения стадиями вершин, фрагментов и косвенных команд до
записей transfer и делают записи видимыми последующей отрисовке. Кадр
удерживает свои буферы и набор дескрипторов до завершения работы графической
очереди. Отмена подавляет публикацию кадра, а отправленные правки сцены
остаются действительны для следующего кадра. См. [воспроизведение S3](bench.md#r23-scene-checks).

<a id="r24-culling"></a>

## R2.4. Отсечение на GPU

Vulkan сообщает `gpu_frustum_culling`, если резидентный путь R2.3
может дополнительно включить `drawIndirectCount`, а устройство поддерживает
шесть дескрипторов буферов хранения в стадии compute и в наборе дескрипторов.
Сцена должна укладываться в `maxDrawIndirectCount` устройства,
диспетчеризацию 65 535 × 128 исполнений и лимит буфера хранения.
Для более крупной сцены используются серии команд R2.3. Прямые снимки,
растровые проходы сцены Custom и устройства вне требований резидентного
пути используют существующий развёрнутый поток и совместимые материалы.

Compute читает границы мешей из пула, принятые матрицы инстансов и серии
команд. Он отсекает границы вне текущей камеры и уплотняет оставшиеся
команды в опубликованном порядке. Каждый штатный растровый проход сцены
выполняет один `vkCmdDrawIndexedIndirectCount`. Цветовой проход использует
общий для всех мешей возрастающий поток индексов, чтобы адресовать углы
треугольников в действующем пуле. Так сохраняются плоские нормали граней,
опубликованные ID объектов и треугольников и первая поверхность при
равной глубине. Привязки проходов Custom остаются совместимыми.

`hiz_occlusion_culling` дополнительно требует семплируемый буфер глубины
D32. Первая фаза рисует только глубину непрозрачных кандидатов, чьи
расширенные экранные границы достигают 32 пикселей по обеим осям. Вторая
фаза сверяет остальных кандидатов с пирамидой максимумов этой глубины.
Непокрытые семплы дают дальнюю глубину, нечётные края изображения
учитываются, а границы, пересекающие ближнюю плоскость, остаются
кандидатами. Для отсечения нужен строгий зазор по глубине по всей
проекции границ. Пирамида каждый кадр использует текущую камеру и
матрицы, поэтому после движения или удаления заслоняющего объекта
устаревшая глубина не сохраняется. Если семплируемое изображение или
пирамида выходят за лимиты кадра, остаётся отсечение по пирамиде видимости.

Графическая очередь упорядочивает обе фазы, загрузки резидентных данных
и вызовы графа. Временные команды и буфер глубины принадлежат слоту
производителя. Незавершённые и переданные на отложенное освобождение
кадры удерживают своё поколение pipeline. Команды и их число остаются
на GPU. При включённой диагностике три 32-битных счётчика читаются
после завершения кадра, без ожидания на потоке рендера. Player без исходников
получает внутренние варианты SPIR-V при экспорте.
См. [эталонные проверки и нативный S3](bench.md#r24-culling-checks)
и [требования Khronos к indexed indirect count](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdDrawIndexedIndirectCount.html).

[Свидетельства R2.4 на Windows](evidence/r24/README.md) подтверждают исходный
критерий по среднему интервалу. В S3-100k средний интервал составил 1,764 мс
с предзаполнением Hi-Z текущего кадра и 1,733 мс без отсечения. В каждой из
трёх серий Hi-Z было по одному превышению бюджета длительностью 20,6348,
20,8540 и 20,6695 мс. В отдельной сцене с перекрытиями список сократился с
2052 кандидатов до 4 при точном совпадении RGBA с эталоном. Парных замеров
времени с отсечением и без него нет. В последующих критериях 60 FPS интервал
свыше 1000/60 мс означает непрохождение, если критерий заранее не задаёт
допустимое число или долю превышений и предел для худшего интервала.
Указывайте обе величины.

## Эталонный GPU и границы замеров

На доступном ПК с Windows x64 (сборка ОС `10.0.26300.10075`) обнаружено одно
физическое устройство Vulkan, RTX 4080 SUPER (`10de:2702`, 16 376 МиБ по
`nvidia-smi`). Драйвер NVIDIA **617.42**, Vulkan устройства **1.4.351**,

## Кандидат в минимальную карту и чек-лист перед выпуском

Настольная GTX 1660 SUPER — кандидат для проверки уровня A на Windows.
Это карта Turing с 6 ГБ GDDR6 и поддержкой API DX12, которую NVIDIA указывает
в примечаниях к выпуску драйвера Vulkan 1.4. Это основания проверить на ней
текущий путь Player с двумя API. Чек-лист перед выпуском охватывает точные
биты возможностей, работу с общим изображением и производительность.
6 ГБ — характеристика этой модели. Минимальный объём VRAM ещё предстоит
измерить. B/C остаются необязательными для базовых игр. У нагрузочной S5
свои цели в дорожной карте. См.
[характеристики карты NVIDIA](https://www.nvidia.com/en-gb/geforce/graphics-cards/compare/?section=compare-specs)
и [поддержку драйвером Vulkan NVIDIA](https://developer.nvidia.com/vulkan-driver).

- [ ] На ПК с физической GTX 1660 SUPER и подключённым к ней монитором записать
   сборку ОС, CPU, ОЗУ, драйвер, режим экрана и профиль питания. Сохранить
   полный вывод `vulkaninfo` и `nvidia-smi`. Сверить биты A и расширение Win32,
   затем убедиться, что интерфейс и производитель кадров используют эту карту.
- [ ] Экспортировать фикстуры G1 и ARPG как standalone Player с Vulkan. Запустить
   обе игры на целевом ПК из перенесённых каталогов с чистыми профилями. Войти
   в Playing, изменить размер окна и подтвердить обычный вывод целиком на GPU
   без ошибок моста. Пакеты должны запускаться без Editor и компиляторов.
   Сохранить результат запуска и хеши пакетов. Нативный отчёт Player собрать
   через `--benchmark` из пакета ARPG. См. [Player](player.md).
- [ ] Замерять только S1 и S2, последовательно на незагруженном рабочем столе,
   через команду `--bench-scene S1|S2 <new output folder>` сборки Editor
   в Release с фичей `bench` по [протоколу бенчмарков](bench.md).
   Задать `MODULE_ENGINE_GUI_VSYNC=off`, `MODULE_ENGINE_BENCHMARK_FRAMES=240`,
   `MODULE_ENGINE_BENCHMARK_ARM=automatic` и `MODULE_ENGINE_BENCHMARK_PROFILING=off`.
   Использовать штатный нативный GUI.
   Для каждой сцены сохранить три полных прогона в отдельных процессах,
   по 30 кадров прогрева и 240 замеренных кадров. Записать фактические
   1920×1080, состояние Playing, 20 активных врагов в S2, фактический режим
   показа, путь вывода целиком на GPU, хеши исходников и бинарника и пик
   рабочего набора процесса S1 по данным ОС. В каждом прогоне среднее
   и p95 должны быть ≤16,67 мс для S1 и ≤16,667 мс для S2. Пик S1 должен
   быть ≤1 ГиБ. Сохранить и тайминги тика S2. Перед выпуском версии,
   которая использует новый путь A, повторить проверку на нём.

Публиковать минимальные требования можно после прохождения этих проверок
на указанной конфигурации. Другие пары GPU и драйвера и физический GPU под
Linux требуют отдельных прогонов.
