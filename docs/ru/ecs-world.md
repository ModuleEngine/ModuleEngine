# ECS-хранилище игрового мира

[English](../ecs-world.md) | [Русский](ecs-world.md) | [Документация](README.md)

`GameState.world: EcsWorld` владеет изменяемыми игровыми данными. В R1.2 у каждой
нативной записи есть неизменяемый компонент Bevy `StableId(u64)`. Закрытый
упорядоченный индекс связывает стабильный ID с `Entity`, содержащим поколение.
Трансформация, родитель, цвет, именованные ссылки и демонстрационное движение
хранятся в этой записи. `Transform` — типизированный компонент Bevy с рефлексией
и переносимым кодеком в [`ComponentRegistry`](component-schemas.md) Core.
Значения компонентов со схемами остаются в JSON-колонках с ключами по стабильному ID.

## Доступ модулей

Native-системы выбирают состав сущностей до чтения значений:

```rust,ignore
let world = &context.world("world")?.world;
for id in world.entities_with(&["example.spin"]) {
    let settings = world.component(id, "example.spin").unwrap();
    let object = world.object(id).unwrap();
    // Stage portable WorldCommands, or edit a component in this tick's world.
}
```

`entities_with` пересекает колонки компонентов, начиная с самой маленькой,
и возвращает стабильный порядок ID. Пустой набор требований выбирает все сущности. Динамические
значения остаются JSON, описанным зарегистрированными схемами компонентов.
Планировщик относится к R1.5.

`component_mut`, `insert_component`, `remove_component`, `transform_mut` и
`references_mut` изменяют представление канонического мира в текущем тике. Native-система может подготовить промежуточные
значения, но весь tick должен пройти структурную проверку, проверку ссылок и активных схем
до публикации. `upsert_entity` заменяет полный граничный DTO,
не начиная новую жизнь объекта; его ссылки проверяются на
границе публикации, что позволяет пакету создавать взаимно ссылающиеся объекты.

`entities_snapshot` и `entity` возвращают владеющие данными DTO `GameEntity` для Inspector,
сериализации, IPC и валидации. Изменение такого DTO не меняет мир.
Примените его явно или отправьте команды. Native hot loops используют запросы по колонкам.

## Время жизни и транзакции

Удаление поддерева очищает колонки и исходящие ссылки каждого удалённого объекта.
Сохранившиеся ссылки на удалённые цели блокируют публикацию, пока не будут явно
очищены. Удаление и создание того же ID начинает новую жизнь: старые компоненты,
ссылки и демонстрационная угловая скорость не могут попасть в заменяющий объект.
При удалении запись исчезает из индекса стабильных ID. Новый ID может получить тот
же слот Bevy с другим поколением, а ссылка на удалённый ID остаётся неразрешимой.
Обычное обновление сохраняет запись и время жизни. При отклонении структурного
изменения записи и индекс остаются в прежнем состоянии.

При публикации с удалением записей Core один раз продвигает буферы уведомлений
Bevy об удалённых компонентах. Закрытый мир хранит уведомления последней
публикации и переиспользует буферы. Это относится к фиксированному тику,
а также к переносимым командам и `clear()` вне тика.

`lifetime(id)` обозначает текущую runtime-инкарнацию отдельно от
сохранённого ID. Клонирование checkpoint сохраняет её; создание, восстановление из DTO или
очистка и повторное создание объекта дают новый токен. Кеши модулей используют этот
токен, чтобы отбрасывать cooldown и death markers объекта при повторном использовании ID. Токены —
локальные для процесса служебные данные, исключённые из семантического сравнения миров и сохранённого
формата DTO сущности. Дескрипторы Bevy принадлежат одному миру. Клон контрольной
копии строит собственный индекс и сохраняет токены времени жизни.

Намерения текущего tick и начальные позиции столкновений также содержат инкарнацию.
Исходная система, вставленная между авторскими этапами, может заменить объект, поэтому эти
временные записи не могут безопасно использовать только его сохранённый ID. Зафиксированные боевые визуальные эффекты
сохраняют исходную роль/стиль, а запросы целей или вспышки попаданий не привязывают
предыдущее действие к заменяющей сущности.

Во время фиксированного тика исполнитель хранит последние принятые записи
Bevy и колонки JSON в режиме чтения. Первый изменяемый доступ к сущности
заносит её запись в журнал. Запросы сразу видят подготовленные записи, новые
инкарнации и удаления в авторском порядке систем. Буфер переносимых команд
проверяется целиком до внесения его изменений в журнал. Custom Rust по-прежнему
получает IPC DTO мира. Его буфер команд мира вносится в журнал после проверки
остальных выходных данных.

При успехе исполнитель проверяет кандидата, публикует команды совместимого
provider, если он выбран, выполняет хуки фиксации систем и применяет журнал
к канонической ECS. При ошибке исполнитель отбрасывает журнал и восстанавливает
переносимое состояние систем, ресурсы, события и метаданные сессии. Существующие
хуки отката восстанавливают внешние данные, включая опубликованное состояние
Rust-воркера и команды управления рендером. Повтор начинается с последнего
принятого тика.

Транзакции неизменённого ECS-мира без активных семантических валидаторов
для имеющихся компонентов не нужен обход сущностей.
При обычных записях проверяются затронутые объекты и именованные ссылки.
Изменение топологии или полная замена мира могут требовать полной проверки
структуры и ссылок. При изменениях в мире с активными схемами компонентов
сохраняется полная проверка схем при наличии таких компонентов, включая
ссылки на другие объекты. Семантические валидаторы исходных модулей для
имеющихся активных компонентов работают и без изменений мира, поскольку
могут читать внешнее состояние. Проекция совместимого provider,
снимок Custom Rust для IPC и снимки презентации в `GameHost::step` с рендером
могут по-прежнему обходить мир. Явные копии для рабочих данных жизненного
цикла и операций со сценами сохраняют своё поведение.

У ECS-сессии по умолчанию нет второго provider. Object-миры и явно
зарегистрированные сторонние миры остаются совместимыми проекциями переносимых данных
объектов. Их validation/commit/rollback по-прежнему участвуют в публикации, а
их частные кеши сохраняются между обычными tick. Новые игровые возможности относятся к
канонической ECS.

## Совместимость сохранений

Wire-представление `GameState` по-прежнему использует карту `entities` от стабильных ID
к DTO, упорядоченную по стабильному ID. Загрузка отклоняет нулевые, повторяющиеся
и несовпадающие ID, некорректную иерархию, неконечные трансформации и отсутствующие
цели именованных ссылок до возврата мира. Авторские файлы сцен, экземпляры префабов
и данные запечатанного Player сохраняют прежний формат. GameHost передаёт ID,
родителей и имеющиеся [именованные ссылки](custom-rust.md#named-object-references)
через Rust IPC как точные значения `u64`. Переносимые данные не содержат дескрипторов Bevy.

```sh
cargo test --offline --locked --release -p module-engine-host --lib r14_tick_rejection -- --test-threads=1
cargo test --offline --locked --release -p module-engine-host --lib r14_s3_tick_cost -- --ignored --nocapture --test-threads=1
```

Проверка отказа выполняет принятый тик, затем неудачный тик, в котором поздняя
система читает записи ранней, заменяет корень поддерева и возвращает ошибку.
Проверяются принятый мир и токены инкарнаций, состояние, ресурсы и события,
после чего тик повторяется без добавления времени. Тесты скомпилированного
Rust в Host проверяют откат состояния воркеров и управления рендером, а также
публикацию принятых событий.

Замер запускает авторское расписание в `GameHost` с нейтральным CPU-рендером
и каноническим `world.ecs`. Он использует ID, трансформации и восемь ECS-компонентов

В каждой ячейке приведена медиана трёх последовательных прогонов Release на

## Проверка R1.3

Запускайте проверки из checkout с полными исходниками, закреплённым
инструментарием и восстановленными офлайн-зависимостями. Выполняйте команды
последовательно.

```sh
python scripts/verify.py --profile contracts --plan
python scripts/verify.py --profile contracts
cargo test --offline --locked -p module-engine-editor component_codec_corpus_roundtrips_through_editor_source_files -- --nocapture
cargo test --offline --locked -p module-engine-editor inspector_noop_apply_respects_sparse_local_values_without_a_prefab
cargo test --offline --locked -p module-engine-editor stable_ids_survive_authored_save_player_export_and_rust_ipc -- --ignored --nocapture
```

Тест записывает исходники дважды штатным сохранением Editor в разные временные
папки. Он сравнивает разобранный JSON с учётом типа чисел, знака нуля,
ключей объектов, наличия полей и порядка массива. Он также проверяет каждую
игровую сцену с установленной композицией и сравнивает восстановленный
нативный ECS с разрешённым DTO. Мини-проект со скомпилированным Rust-воркером
проверяет значения по независимым литералам, включая поле с `u64::MAX`,
буквальный ключ с точкой, явный null, отсутствие поля, знак нуля и эффективную
ось из схемы. Он также проверяет отклонение сохранения, если активному
числовому полю задать null.
Повторное сохранение проверяет замену только знака нуля с минуса на плюс в
обоих файлах, для нативного Transform в сцене и JSON компонента в проекте.

JSON-примеры в репозитории — графы старых форматов без авторских сцен. Тест
сравнивает их копии формата 4 после штатного декодера явной миграции.
Байты исходных файлов сохраняются. Равенство JSON проверяется между двумя новыми
записями принятого документа формата 4. Сравнение с исходным файлом старого
формата остаётся за границами этой проверки. Игровые проверки охватывают `level01`
по `level10` Crate Garden, шаблон Two Arenas и мигрированный
`game-project.json` со сценами `arena` и `boss` в обоих случаях. Старый пин SDK
в `game-project-v4.json` по-прежнему отклоняется. Two Arenas — доступный
технический базис G2. Полная кампания G2 ещё впереди.

Для ручной проверки на Windows создайте **File → New Project → Empty scene**
в отдельной папке. Добавьте объект, задайте X в **Position** равным `1.25`,
добавьте [пример Rotation](component-schemas.md) в **Gameplay Systems** и
привяжите порт `world` и нажмите **Apply graph draft**. Подключите **Rotation** в Inspector и примените
скорость `4`. Нажмите **Create template from selected**. Нажмите
**Apply fields** у экземпляра без правок, затем измените скорость шаблона
на `6` и нажмите **Apply template defaults to instances**. Экземпляр должен
унаследовать `6`, а в **Advanced** JSON карта `overrides` должна остаться
пустой. Сохраните проект, откройте его повторно и нажмите Play, чтобы увидеть
вращение.

## Проверка R1.2

Запускайте из checkout с полными исходниками и восстановленными зависимостями
нативной сборки. Запускайте проверки Editor последовательно, поскольку они
собирают воркеры и Player.

```sh
cargo test --offline --locked -p module-engine-core
cargo test --offline --locked -p module-engine-editor existing_game_project_save_load_save_keeps_exact_bytes -- --ignored --nocapture
cargo test --offline --locked -p module-engine-editor stable_ids_survive_authored_save_player_export_and_rust_ipc -- --ignored --nocapture
```

- Core проверяет отклонение недопустимого пакета и реальное переиспользование
  слота Bevy. Слот удалённой цели получает новое поколение, а старая именованная
  ссылка не разрешается в замену. Существующие тесты покрывают валидацию ID
  и транзакционную публикацию.
- Существующий `game-project.json` использует формат 3. Тест явно мигрирует
  одноразовую копию, сохраняет и загружает формат 4, затем побайтно сравнивает
  сохранённый проект и внешние сцены после второго сохранения. Он также
  сравнивает исходные байты.
- Сквозная фикстура разрешает экземпляр префаба с ID `9007199254740993` и обе
  ссылки на него. Тест сравнивает две независимо записанные копии проекта
  и внешней сцены, экспортирует игру через Editor и запускает нативный Player
  из экспорта. Скомпилированный Rust-воркер читает родителя и цель именованной
  ссылки через IPC и использует ID цели в возвращаемой команде мира. Состояние
  Player подтверждает выполнение команды и сохранение обеих ссылок.
  Сериализация, чтение и повторная сериализация состояния дают те же байты.

Нативная фикстура использует программный рендерер. [Замеры прототипа
R1.1](ecs-storage-decision.md#r11) относятся к его историческому снимку.
