# R0.6 benchmark baseline — 22 November 2026

[English](bench-r06-20261122.md) | [Русский](ru/bench-r06-20261122.md) | [Documentation](README.md)

The first series on `main` after [PR #19](https://github.com/myjname/ModuleEngine/pull/19)
passed repeatability. All 15 scored scene runs completed, with a maximum
spread of **2.39 %** against the **5 %** limit. S1 and S2 met every frame
and memory budget applicable to them in all three runs. This is the
[R0.6 reference](product-roadmap.md#rebuild-r0) for later comparisons.

## Reproduction and conditions

Run from the measured source revision on an idle, unlocked desktop. Use a
native Python interpreter and keep the benchmark window unobstructed.

```sh
python scripts/bench.py --no-profiling
```

- Windows 11 Pro 26H2, build `10.0.26300.10075`, Ryzen 9 3900X
  (12 cores / 24 logical CPUs), 63.9 GiB visible RAM, AMD Ryzen Balanced.
  RTX 4080 SUPER, NVIDIA driver **617.42**, 16,376 MiB reported VRAM.
  The monitor was at 3440×1440, 144 Hz and 100 % scale.
- Native **1920×1080** windows. All S1/S2 observations had window focus and
  valid frame metadata in Playing, with no user input or error frames.
  The Player's optional visibility field was unavailable on this path.
  S2 retained exactly 20 enemies. S3–S5 passed the benchmark's client-size
  and minimized-state checks. All five used WGPU/DX12 for the GUI and the
  Vulkan producer on the same GPU with no CPU pixel readback.
- GUI vsync was requested off. WGPU reported **`Immediate`** for every
  scene in the prewarm and scored runs. This is the configured swapchain
  mode. The intervals below measure application observations. Physical
  scanout and time spent waiting for presentation were outside this protocol.
- A Release build of `module-engine-editor` with `bench`, target
  `x86_64-pc-windows-msvc`, rustc and Cargo 1.99.0, Python 3.12.14,
  `CARGO_NET_OFFLINE=true`. The launcher verified 71 pinned Sponza files
  and recorded the DXC input hashes. Frame profiling was off throughout.
- The launcher started at **00:03 CET** after a background GPU workload
  subsided. In the six one-second samples before launch, only System and
  ChatGPT exceeded 0.35 % on an individual GPU engine (maximum 0.662 %).
  Aggregate NVIDIA readings use a different counter. `gpu.csv` records
  one-second device telemetry from prewarm through the end of the series
  at approximately 00:14 CET. It has no process attribution.
- One unscored S1–S5 prewarm pass followed by three scored passes in fresh
  processes, all sequential. S1–S4 had 30 warmup and 240 measured frames
  per process. S5 had five and 30. S1/S2 report 239 intervals between 240
  observed frames. See the [benchmark protocol](bench.md).

S1 and S2 passed the limit of `1000 / 60` ms on both mean and p95. Their
worst p95 values were 9.641 and 9.327 ms respectively, and S1's highest
working set was 260.1 MiB against 1024 MiB. S3–S5 have no absolute frame
or memory budget in R0.6. The S1 supplemental step spread of 6.85 % is
outside the repeatability criteria defined for S1.

S4/S5 are static and have no gameplay tick. Per-pass GPU timestamps and
the added CPU spans were disabled for this comparison. S4 measured
262,961 triangles with the legacy sun; its 256 point lights are inventory
only until R5, and no accepted reference image exists. S5 measured all
20 million triangles using the legacy expanded vertex stream. Meshlet
counts require R8. The memory table is the OS process high-water mark.
GPU telemetry tracks device-wide memory use. The protocol has no per-process
VRAM figure or editor open-to-first-frame measurement.

## Comparison with R0.2

The fixture inventories match the [accepted R0.2 series](bench-r02-20261121.md).
GPU, driver, render dimensions, monitor settings and vsync request match.
R0.2 predates profiling and did not record its effective present mode.
The timing deltas use the mean of the three run means or the mean of the
three run p95 values, respectively. Positive values mean longer times.

| Scene | Frame mean / p95 change | Step or tick mean / p95 change | Render or submission mean / p95 change |
| --- | ---: | ---: | ---: |
| S1 | +0.00 % / +0.11 % | +0.43 % / +1.18 % | +0.67 % / +1.56 % |
| S2 | −0.14 % / −1.40 % | +0.28 % / +7.38 % | +0.86 % / −1.14 % |
| S3 | +0.41 % / +0.07 % | −3.65 % / −1.93 % | +0.64 % / +1.26 % |
| S4 | +2.51 % / +14.04 % | — | +2.02 % / +2.56 % |
| S5 | +2.09 % / +2.37 % | — | +2.70 % / +3.22 % |

The largest frame-tail change was S4 (47.108 → 53.724 ms, mean of the run
p95s). Its individual p95s ranged from 45.966 to 58.119 ms. The S2 step
p95 rose from 3.679 to 3.950 ms on the same aggregation while its frame
budget still passed. S4's working set rose from 397.5–399.9 to
425.6–427.8 MiB. These are observed differences between snapshots. The
protocol's 5 % spread limit applies to declared means within one series.
The series passed that check. The cause of the observed differences remains
undetermined.

For [R1.1](product-roadmap.md#rebuild-r1), the current Core ECS reference is
**0.756 ms mean** across the runs, with per-run p95 of **0.943–0.976 ms**.
Use the same S3 fixture of 2,000 entities with eight components each when
comparing query, mutation, spawn/despawn and snapshot behavior. One fifth of
the rounded R0.6 mean is about **0.151 ms**. Apply the roadmap's fivefold
criterion to matched old/new measurements and check the authored-data
invariants. The S2 step p95 values above are the R1.8 reference.
