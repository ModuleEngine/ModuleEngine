## Third-Party Code

[`THIRD-PARTY-LICENSES.txt`](../THIRD-PARTY-LICENSES.txt) lists every Rust
package compiled into the Windows and Linux binaries, with its SPDX license
expression and the license and notice texts it ships. Packages used only by
other platforms, and dev-dependencies, are not included. A package without its
own license file gets the standard text of its preferred license; the egui
default fonts add their OFL-1.1, Ubuntu Font Licence, Hack and emoji-font
notices.

[`scripts/third_party_licenses.py`](../scripts/third_party_licenses.py)
generates the file from `Cargo.lock` with the Python standard library and
`cargo metadata`. It also enforces the allowed license list: MIT, MIT-0,
Apache-2.0 (also with LLVM-exception), Zlib, BSD-2-Clause, BSD-3-Clause, ISC,
BSL-1.0, 0BSD, Unlicense, CC0-1.0, Unicode-3.0, Unicode-DFS-2016, OFL-1.1 and
Ubuntu-font-1.0. A package passes when at least one alternative of its
expression uses only allowed licenses. Only crates.io packages are accepted;
git and path dependencies fail the check.

After changing dependencies or `Cargo.lock`, run:

```text
cargo fetch --locked
python scripts/third_party_licenses.py
```

CI runs `python scripts/third_party_licenses.py --check` on both platforms. It
fails when a shipped package uses a license outside the list or the committed
file differs from the regenerated one.

## What Deliveries Include

| Delivery | `LICENSE-MIT`, `LICENSE-APACHE`, `THIRD-PARTY-LICENSES.txt` | DXC `LICENSE-MS.txt`, `LICENSE-LLVM.txt` |
| --- | --- | --- |
| Full source export | Yes, required | Yes, with `tools/dxc` |
| Team export | Yes, required | Yes, when the Vulkan renderer is connected |
| Standalone Player | Yes, required; `README.txt` points to them | Not shipped; Player contains no DXC |

The Player export copies the three files from the engine package that builds it
and fails if any is missing. They are listed and hashed in `player.json` like
the other package files, and a project asset cannot use these names.

## Code Signing

ModuleEngine binaries are not code-signed yet: CI verifies sources but does not
build release binaries, and no signing certificate is configured. Windows
SmartScreen may warn when an unsigned `ModuleEngine.exe` or `Player.exe` is
started on another computer. Signing needs a certificate or a signing service
account owned by the project; it will be added with a release workflow. A
signing key must stay in CI secrets or a hardware/cloud HSM and must never be
committed.
