# Authored scene files

[English](scene-files.md) | [Русский](ru/scene-files.md) | [Documentation](README.md)

## Scope and ownership

The 15 November 2026 follow-up implements separate editable scene files and
rebuilds Hierarchy on that source model. The contract and bounded verification
are recorded here; local evidence is in `outputs/reviews/hierarchy-scenes-20261115/`.

Core owns complete `GameProject.scenes`, scene-local object IDs, parents,
prefabs, component payloads and optional authored names. It performs no scene
file IO. ProjectTools owns the source-file format, loading, publication and
disk conflict checks. Editor selects/edits these documents. Play receives a
separate hydrated copy; opening a view never installs a game mechanic.

Scene files are mutable authored source. They are **not** imported immutable
`AssetManifest` resources. Their accepted byte hashes belong to the open
workspace and must not be rebased through authored Undo or an Assets refresh.

Non-goals: streaming, additive multi-scene editing, cross-scene parenting,
separate prefab files, another world architecture, or new gameplay/rendering.

## Exact file formats

The graph schema remains **4**. File-container versioning is separate:

- Existing inline project: `schema_version: 4`, embedded `game.scenes`, no
  `scene_storage_version` and no nonempty external bindings.
- External project: `schema_version: 4`, exact `scene_storage_version: 1`,
  `game.scene_assets` mapping stable scene IDs to `{ "id", "path" }` bindings,
  and **no** `game.scenes` bodies.
- Each bound file: exact `scene_asset_version: 1`, `scene_id`, `asset_id`, and
  one complete `scene` (`AuthoredScene`). Both identities must match the project.

Mixed inline/external representations and unsupported versions reject. Unknown
typed-record keys reject; opaque component/override payloads keep their unknown
namespaces, explicit nulls and object order. Internal history/checkpoint/merge
and IPC serialization remains hydrated, including both scene bodies and their
bindings. It is deliberately different from authored project-file serialization.

`SceneAssetBinding.id` survives file moves and display-name changes. The scene
map key remains the target of portals and game-owned contracts. Object IDs are
scene-local and never regenerated by a file rename. Paths are normalized,
project-relative `scenes/.../*.scene.json`; aliasing, redirected paths, escape,
duplicate IDs and missing files reject rather than becoming empty scenes.

An object's `name` is author-facing metadata. `AuthoredName` preserves absent,
explicit JSON null and text separately. Merely selecting/inspecting an unnamed
object must not write a generated name or an override. It does not change
`WorldObject` or impose gameplay data on the runtime.

## Opening, saving and copying

Opening an inline project does not convert or write it. Ordinary Save retains
its storage mode. New projects, Save As and an explicit conversion action use
external scene files. Conversion must publish the accepted authored candidate,
not reload or replace unsaved scene content with old disk bytes.

ProjectTools eagerly reads each external file into a separate candidate. Only
after exact format/identity checks and the application's composition, source,
SDK, profile and scene validation may Editor adopt the candidate. A missing or
malformed file keeps the already open project and its state.

The workspace retains accepted project/scene byte hashes (`ProjectFileState`).
Before writing, current bytes must match that generation; new target paths must
be absent. A refresh cannot silently adopt externally changed bodies or hashes.
Reload is explicit; Save As can preserve the current authored work separately.

Publication uses durable originals and rollback-capable file transactions.
The project DTO is published last. A resource rename that changes a scene's
references includes that scene file and project metadata in the same rollback
unit. Unchanged scene files are not rewritten. Failed publication retains the
previous authored document, history cursor and accepted generation; recovery
snapshots may remain in `.asset-history/`. This is not a process-crash atomicity
guarantee for a populated multi-file workspace.

Save As serializes **current in-memory bodies**, not stale source-file copies.
Every Save As to a different project path allocates a fresh scene subtree,
including a confirmed repeat overwrite of an existing copy. It remaps paths
while retaining scene/object/asset IDs in the copy. A backed-up previous project
DTO continues to refer to its own unchanged scene files. Subsequent edits must not change the original project's scenes.
New source groups are allocated independently of the project's display name.

## Undo, deletion and packages

Ordinary scene edits/Undo remain in memory until Save. File operations have an
explicit history boundary and update files and project together. Replaying one
after a later successful scene Save uses the target hydrated history snapshot
and the latest accepted disk generation; it must not mistake our own Save for
an external edit or relax immutable resource checks.

Scene deletion first validates entry/transition/game-owned references. A used
scene is not silently detached. Source originals are retained in the project
trash with identity; restore must validate collisions, payload, dependencies
and ownership. Failure or cancellation preserves the previous project.

Editable Full/Team deliveries contain actual authored scene files. Team's
frozen architecture, source/SDK restrictions and permitted game authoring remain.
Player deliberately uses a sealed **embedded runtime projection** with source
bindings removed; it needs no editor or scene compiler. A runtime projection
does not become another editable source authority.


## Editor navigation and Hierarchy

Use **File → Scene** or the **…** menu beside the current scene in Hierarchy for
New, Open, Duplicate, entry selection, rename, move, delete and conversion.
Old inline projects retain their storage mode on ordinary Save; **Convert
embedded scenes to files…** is explicit. The file operations use the save-first
guard, real background operation status and file Undo/Redo. Deleting the entry
scene is unavailable until another entry is chosen.

Assets lists registered `.scene.json` sources separately from imported resources.
Double-click opens a scene; it does not add its objects to another scene. Context
actions and the details region operate on its stable identity. A move may create
a destination under `scenes/`; generic Import/New folder is disabled in source
folders with an explanation. Trash restoration retains identity and exact
unmodified source bytes. External changes require explicit reload or Save As;
Refresh diagnoses them without adopting them.

Hierarchy has a current-scene selector/menu, search, one Add-object icon and
object/entry metadata. It has no permanent scene-name/duplicate/delete button
stack or repeated title. Rows occupy the full available width, are 28 logical
points high and indent children by 16. A disclosure toggles actual children;
search temporarily reveals matching objects and their ancestors. Names come
from authored `name`, then prefab identity, then `Object <id>`; the engine does
not infer game-specific roles. ID, parent, prefab and component keys are in the
hover detail. The selected name also appears in Inspector.

Click a row to select the shared Scene/Inspector object. **F2** or its context
menu opens Rename; **Delete** removes the object and descendants as one validated
Undo, clearing existing same-scene references through the existing deletion
contract. Text fields retain their keys. Rename has Apply/Cancel and a stale
scene check; it changes display metadata only and writes on Save. Applying an
unchanged empty name preserves absent/null. Play blocks authored edits. Search,
folding and selection do not save, clone the complete document or prepare a host.
Changing to another scene clears object selection even when it reuses an ID.

In an area shorter than 180 logical points, search and Add object move into **…** and the count row is omitted, keeping room for object rows. An active search marks the scene caption as filtered.

Search/folding are transient view state, not project data. Additive loading,
multi-selection, object drag reparenting and scene streaming remain outside this
slice; parent editing stays in Inspector. The **Project File** window explicitly
shows expanded project data including loaded scene bodies, not the external
project DTO verbatim.
